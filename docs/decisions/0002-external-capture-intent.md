# 0002: 外部入力は録画の目標状態として受け取る

## 状況

30分のチャンク終了後は自動で次の録画を開始しながら、装着者が休憩に入るときはいつでも停止し、戻ったときはいつでも再開できる必要があります。装着者が対象アプリを直接操作すると、自動操作と実指の入力順序を保証できず、想定外の画面遷移や二重操作が起こります。

一方、現在の`xcodebuild test`は、あらかじめ書いた一連のテストを完了させる実行方式です。録画中にMac側から任意の指示を継続的に受け取る通常運転の境界にはしません。

## 決定

ユーザーの入力は、Macコントローラー上の`running`または`paused`という目標状態として受け取ります。入力からiPhoneのタップを直接発火しません。

端末ごとに一つだけ存在するDevice Workerが、対象アプリの現在画面と最新の目標状態を照合し、必要な操作を一つずつ直列に実行します。

| 目標状態 | 現在画面 | 操作 |
| --- | --- | --- |
| `running` | ホーム | タスクを開く |
| `running` | 開始待ち | 録画を開始する |
| `running` | 録画中 | 何もしない |
| `paused` | 録画中 | 録画を停止する |
| `paused` | 開始待ち | ホームへ戻る |
| `paused` | ホーム | 何もしない |

録画中に30分チャンクが自然終了してホームへ戻った場合、目標状態が`running`なら次のチャンクを開始します。`paused`ならそのまま待機します。ログイン、権限要求、警告、未確認画面では操作せず`needs_attention`へ移ります。

通常運転では、実機上でHTTP命令を受けるWebDriverAgentをAppium XCUITest Driverから利用し、Mac側に長時間の制御セッションを維持します。既存のXCUITestテストケースは画面要素とアダプターの検証に残しますが、ユーザー入力を受け取る常駐制御ループには使いません。

## 入力競合の扱い

- 一台のiPhoneへ操作を送れるDevice Workerは一つだけにする。
- Mac UI、CLI、物理ボタンなど全ての入力元は、タップ命令ではなく同じ目標状態を書き換える。
- 新しい入力は古い入力をキューに積み重ねず、最新の目標状態で上書きする。
- 送信済みの一回のタップは取り消せないため、操作完了後に目標状態が変わっていれば、次の観測で逆方向へ収束させる。
- 装着者は対象アプリを直接操作しない。実指をOSレベルで排他する仕組みとはみなさない。

## 未確定事項

Minute Dataにおける録画中画面、手動停止後の画面、30分自然終了後の画面は、提出を伴わない検証環境または運営の許可を得たテストで確定する必要があります。それまではモックアプリだけで開始・停止・自動再開を検証します。
