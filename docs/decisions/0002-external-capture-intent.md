# 0002: 外部入力は録画の目標状態として受け取る

## 状況

30分のチャンク終了後は自動で次の録画を開始しながら、装着者が休憩に入るときはいつでも止め、戻ったときはいつでも再開できる必要があります。装着者が対象アプリを直接操作すると、自動操作と実指の入力順序を保証できず、想定外の画面遷移や二重操作が起こります。

一連の操作をあらかじめ固定したUIテストは、録画中にMac側から任意の指示を継続的に受け取る通常運転の境界にはなりません。

## 決定

ユーザーの入力は、Mac側の`running`または`paused`という目標状態として受け取ります。入力からiPhoneのタップを直接発火しません。

端末ごとに一つだけ存在するDevice Workerが、対象アプリの現在画面と最新の目標状態を照合します。`OperationDefinitionAdapter`が操作定義の地図から目標までの道順を計算して次の一歩を選び（[0004](0004-route-planning.md)）、Device Workerはその実行を一つずつ直列に進めます。

録画が上限の長さで終わって完了画面になると、目標状態が`running`なら保存または破棄をして次の録画を始め、`paused`なら操作定義の止めた状態で待ちます。どの状態にも当てはまらない画面、iOSのダイアログ、何かに覆われた部品では操作せず、`needsAttention`へ移ります。

通常運転では、実機上のWebDriverAgentをAppium XCUITest Driverから利用し、Mac側に長時間のHTTPセッションを維持します。一回限りのXCUITestシナリオを通常運転へ使用しません。

## 入力競合の扱い

- 一台のiPhoneへ操作を送れるDevice Workerは一つだけにする。
- Mac UI、CLI、物理ボタンなど全ての入力元は、タップ命令ではなく同じ目標状態を書き換える。
- 新しい入力は古い入力をキューに積み重ねず、最新の目標状態で上書きする。
- 送信済みの一回のタップは取り消せないため、操作完了後に目標状態が変わっていれば、次の観測で逆方向へ収束させる。
- 終了の指示も目標状態を`paused`へ変える入力として扱う。送信済みの操作が終わるのを待ち、止めた状態まで進めてから受け付けを止める。Ctrl-C、終了要求、ターミナルの終了も同じ終了の指示として扱う。
- 装着者が画面を触っても、次の一歩は触った後の画面から決める。ただし、自動操作と同時に触ると想定外の画面になることがあり、そのときは止まる。実指をOSレベルで排他する仕組みとはみなさない。

## 完了操作の境界

破棄、保持、提出は外部状態への影響が異なります。Device Workerは各操作の影響を記録できる型を持ち、録画完了後の処理はアプリ別操作定義の操作と遷移で指定します。

完了画面で保存するか破棄するかは操作定義の`afterRecording`で選び、共通のDevice Workerと実行処理は変えません。
