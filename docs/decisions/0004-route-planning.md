# 0004: 操作定義は画面遷移として記述し、経路は毎回計算する

## 状況

当初の操作定義は、ホーム・録画開始前・録画中・録画完了後の4画面と、目標状態ごとに各画面でタップするボタンの対応表でした。装着者や周囲の人が画面に触れて別のタブやダイアログに遷移すると、対応表にない画面になり、そこで停止していました。

Minute 1.29.0を実機で調査したところ、撮影の1サイクルには次の画面がありました。

- タスク一覧と、他の2つのタブ
- タスクカード
- 録画待機
- カウントダウン
- 録画中
- 録画完了画面
- 保存・破棄・1分未満の録画の3つの確認ダイアログ
- 保存後の画面

ダイアログはいずれも、背後の画面のUI要素を残したまま重なって表示されます。カウントダウンの終了と、上限時間での録画の終了は、タップしなくてもアプリが自動で遷移します。

## 決定

操作定義には、状態（画面の識別条件）、操作（どの状態で何をタップするとどの状態に遷移するか）、アプリによる自動遷移、目標状態を記述します。手順の順序や、画面ごとの対応表は記述しません。

実行処理は、画面を読み取るたびに現在の状態から目標状態までの経路を計算し、最初の操作だけを実行します。どの画面から開始しても、途中で人が画面に触れても、次の操作は常に現在の画面から決定されます。

経過時間からアプリの状態を推定しません。録画の終了は、録画中の画面が録画完了画面に変わったことで検知します。時間を使用するのは、画面の読み取り間隔と、タップ後に画面の変化を待つ上限時間のみです。

録画を保存するか破棄するかは、操作定義の`afterRecording`で指定します。経路の計算では、指定しなかった側の操作を使用しません。

## 結果

- 定義の検証時に、すべての状態から両方の目標状態への経路があることを確認できる
- 未定義の画面、何かに覆われたUI要素、iOSのダイアログでは、タップせずに停止する
- 背後の画面の状態には、重なるダイアログの文言を`absent`として記述する必要がある
- 一覧からタスクを検索する操作はスクロールを伴い、数十秒かかる。撮影継続中は一覧に戻らないため、画面操作の後の復旧時にのみ使用する
