# 0004: 操作定義は画面のつながりとして書き、道順は毎回計算する

## 状況

当初の操作定義は、ホーム・開始前・録画中・完了後の4画面と、目標状態ごとにその画面で押すボタンの表でした。装着者や周りの人が画面を触って別のタブやダイアログに移ると表にない画面になり、そこで止まっていました。

Minute 1.29.0を実機で調べると、撮影の一周には次の画面がありました。

- タスク一覧と、ほかの2つのタブ
- タスクの説明カード
- 録画待機
- カウントダウン
- 録画中
- 完了画面
- 保存・破棄・1分未満の録画の3つの確認ダイアログ
- 保存後の画面

ダイアログはどれも、下の画面の部品を残したまま重なります。カウントダウンの終了と、上限の長さでの録画の終了は、押さなくてもアプリが進めます。

## 決定

操作定義には、状態（画面の見分け方）、操作（どの状態で何を押すとどの状態へ移るか）、アプリが自分で進む移り変わり、目標の状態を書きます。手順の並びや、画面ごとの対応表は書きません。

実行処理は、画面を読むたびに今の状態から目標までの道順を計算し、最初の一歩だけを実行します。どこから始まっても、途中で人が画面を触っても、次の一歩は必ず今の画面から決まります。

経過時間からアプリの状態を推測しません。録画の終了は、録画中の画面が完了画面に変わったことで知ります。時間を使うのは、画面を読む間隔と、押した後に変化を待つ上限だけです。

録画を保存するか破棄するかは、操作定義の`afterRecording`で選びます。道順の計算は、選ばなかった側の操作を使いません。

## 結果

- 定義を検証するときに、すべての状態から両方の目標へ道順があることを確かめられる
- 地図にない画面、何かに覆われた部品、iOSのダイアログでは押さずに止まる
- 下の画面の状態には、重なるダイアログの文言を`absent`として書く必要がある
- 一覧からタスクを探す操作はスクロールを伴い、数十秒かかる。撮影を続けている間は一覧に戻らないので、画面を触られた後の立て直しでだけ使う
